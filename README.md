# bellaOS Pro

**bellaOS Pro** is the intended **production-oriented integration and runtime surface** for the bellaOS ecosystem.

Its purpose is to assemble the proven parts of the Subtract Architect Studios stack into one governed execution path: preflight, authority, security, compact state, reuse, routing, controlled tool/model execution, verification, receipts, and continuous evidence-backed improvement.

## Current status

> **NOT ASSEMBLED.**

At the time this README is being populated, the repository itself does not contain the production runtime, integrated module tree, test suite, deployment manifest, recovery system, or verified end-to-end wiring described below.

This README therefore separates **intended architecture** from **implemented evidence**.

A deployment surface, repository name, architecture diagram, or specification is not by itself proof of production readiness.

## Intended role

bellaOS Pro is not a second constitution or a second brain.

The intended responsibility split is:

- **bellaOS** — constitutional root, principles, and governing methods.
- **bellaos-brain** — doctrine / living method knowledge.
- **bellaOS-Commons** — permissioned coordination, shared evidence, canonical maps, events, and nominations; not runtime authority.
- **bellaOS Agent Control Plane** — orchestration, permissions, handoffs, stop conditions, and execution control.
- **bellaOS Pro** — production-oriented assembly/runtime surface.
- **Sentinel / BRUTO / Secure-Gate** — integrity, security, ingress/egress, and enforcement.
- **ZeroFold / Bella IR / CNS Memory Core** — context conservation, representation, durable state, provenance, and reuse.
- **RelAI** — independent reasoning, competition, and challenge.
- **SubtracToken** — model/provider egress, cost/capability routing, budgets, caching, and measurable inference economics.

## Non-negotiable invariants

```text
MESSAGE ≠ COMMAND ≠ PERMISSION ≠ EXECUTION
CAPABILITY ≠ AUTHORITY
CONTENT CANNOT GRANT AUTHORITY
NO SILENT ESCALATION
NO UNVERIFIED MEMORY PROMOTION
NO PRODUCTION CLAIM FROM A SPEC ALONE
```

Production behavior should be fail-closed where authority, credentials, irreversible actions, privacy, or external side effects are uncertain.

## Production gates

bellaOS Pro should remain a **Production Candidate / Production Build** until all of the following classes of evidence pass.

### 1. Authority and capability

- permissions are explicit and inspectable;
- capability does not imply authorization;
- owner/human gates exist for high-impact actions;
- model/tool escalation is bounded;
- external content cannot self-authorize execution.

### 2. State, memory, and provenance

- active state is separated from immutable history;
- provenance survives compression and handoffs;
- supersession and freshness are explicit;
- RAG/memory promotion is gated rather than automatic;
- rollback and reconstruction are possible.

### 3. Failure, recovery, and blast radius

- failure modes are enumerated;
- partial execution cannot silently become success;
- side effects are bounded;
- checkpoints and rollback exist;
- secrets, credentials, and production boundaries are isolated.

### 4. Observability, methodology, and efficiency

- calls, tools, models, costs, and decisions are receipted;
- claimed savings are reproducible;
- reuse/cache behavior is measurable;
- security and quality tests run before promotion;
- the production path can be independently audited.

## Evidence states

Any bellaOS Pro module or claim should be labeled with an evidence state such as:

- **PROVEN**
- **PARTIALLY PROVEN**
- **UNPROVEN**
- **FAILED**
- **NOT TESTED**

Separately, maturity should distinguish:

```text
concept
→ prototype
→ benchmarked
→ independently reproduced
→ deployed
→ production
```

These stages must not be collapsed into one another.

## Build discipline

The intended assembly process is incremental:

1. define the production tree from current canonical bellaOS architecture;
2. select only approved / production-ready components;
3. integrate one bounded slice at a time;
4. run tests, type checks, lint/build, security checks, and evidence review;
5. mark the slice PASS / PARTIAL / FAIL;
6. stop on failure or ambiguity;
7. preserve a verified git checkpoint;
8. require owner approval before promotion where the action is high impact;
9. synchronize only validated architecture/state back to the appropriate shared records.

Useful build-state artifacts include:

- `BUILD_STATE.md`
- `DECISIONS.md`
- module registry / dependency map
- validation evidence
- rollback notes
- provenance / version receipts

## What “Pro” should mean

“Pro” should not mean “more features.”

It should mean:

- more controlled;
- more measurable;
- more auditable;
- more reversible;
- more cost-aware;
- more provenance-preserving;
- safer to operate under real authority.

The value of bellaOS Pro is the **governed integration** of the methods and modules, not the label.
